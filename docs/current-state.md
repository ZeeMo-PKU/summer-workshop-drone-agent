# 当前实现审计

审计时间：2026-08-05

## 已验证功能

- 编译后的服务器程序包含 `Front` 与 `PodVisibleLight` 双通道逻辑。
- 实际测试成功生成两轮题目照片和两轮答题布局照片，全部为 1280x720 JPEG。
- `PhysicalAnswerZone`、`answerZoneName` 和 `flyToAnswerZone` 已覆盖 A/B/C 三个物理位置。
- 答题流程已改为“B 中间观察点拍照 -> 目标槽 -> 投球 -> 返回启动区”。

## 关键问题

1. 下摄数据链路已恢复，但构图方向仍不正确

   2026-08-05 13:16 通过重启吊舱设备恢复了 `ov48` RTSP，官方 SDK 连续取帧 3/3 成功、0 次超时。新照片清晰，但 `gimbalDownSet` 返回成功后仍拍到天花板，说明方向映射、安装姿态或预置位定义需要校准。恢复证据与安全操作流程见 [下摄实时流恢复](camera-recovery.md)。

2. 识图尚未接入

   题目事件仍打印 `answer logic is not implemented`；布局照片保存后没有被读取。目标位置在事件处理处硬编码为物理 A。

3. 拍照失败仍继续投球

   `captureAnswerLayoutPhoto` 失败后，程序只记录日志，然后继续前往选定区域并打开夹爪。开发阶段应改为取消投球并返航或悬停。

4. 默认执行风险

   `bool execute = true` 与帮助中的默认 dry-run 不一致。应改成 `false`，强制显式 `--execute`。

5. 文案与行为不一致

   起飞常量是 1 m，但注释和日志仍写 3 m；帮助写默认 answer-B，但当前源码硬编码物理 A。

6. 源码和二进制不同步

   检查时源码修改时间为 10:15，二进制为 10:09。二进制包含双摄和 B 观察点逻辑，但最后六分钟的源码变化是否编译无法确认。

7. 照片可能被覆盖

   文件名只包含轮次。程序重新启动后会再次生成 `round_1_*`，覆盖上一次同名照片。建议增加本次运行的时间戳目录。

## 推荐顺序

1. 修复默认执行、文案和拍照失败策略。
2. 调整下摄朝向与观察点，收集可用布局照片。
3. 把物理位置重命名为 Zone1/Zone2/Zone3，避免与答案 A/B/C 混淆。
4. 离线实现并测试题目识别、布局识别与答案映射。
5. 在仿真环境接入完整流程。
